# Session (14): Tooling in Embedded Systems & The C Build Process

Learned (mixed with personal research from Tooling.pdf):

Note:
````
    This session completely demystifies the embedded toolchain, mapping out the exact sequence 
    of how a raw C source file is translated into physical machine code and loaded into a 
    microcontroller's memory. It bridges abstract software with hardware reality, breaking down 
    object file sections, Linker symbol tables, and the critical pre-main() Startup Code.
````

${\color{red}\text{VERY IMPORTANT NOTE: (1)}}$
````
    There is a profound illusion in standard C programming: the belief that execution begins at main().
    In embedded systems, main() is simply a destination. Before main() is ever called, the microcontroller 
    must physically organize its memory to match the assumptions made in the code.

    This introduces the "Startup Code"—the true first code to run on a microcontroller.
    Its responsibilities include:
    1. Copying initialized data (.data) from Flash into RAM.
    2. Reserving space for uninitialized data (.bss) in RAM.
    3. Initializing the .bss section with Zeros.
    4. Initializing the Stack Pointer.
    5. ONLY THEN does it call main().
````

<br>

&emsp; ${\color{red}\text{(1)}}$: **The Build Process Pipeline**
<br>

&emsp;&emsp; ${\color{blue}\text{(1.1)}}$: **Preprocessor**  
````
            The Preprocessor is a text-replacement tool that operates before true compilation.
            It handles two main types of directives (starting with '#'):
            1. Path/Macro Comments: e.g., #include, #define.
            2. Compiler Directives: e.g., #pragma (Compiler-dependent, such as Linux vs Windows targets).

            It outputs an "Intermediate File" (.i).
            Terminal Command to stop after Preprocessing (can use -P to remove comments):
````
```bash
                gcc -E file1.c -o out.i
```
<br>

&emsp;&emsp; ${\color{blue}\text{(1.2)}}$: **Compiler**  
````
            The Compiler translates the intermediate C code into human-readable Assembly Code (.asm).
            It acts as the primary gatekeeper, performing strict code analysis:
            1. Tokenization: Breaking code into understandable chunks (e.g., int x = 5;).
            2. Syntax Analysis: Catching structural errors (e.g., int 3x = 8; -> Syntax Error).
            3. Semantic Check & Parsing: Translating logic into Assembly.
            4. Optimization: Refining the code for speed or size.

            Example Assembly Translation:
            z = x + y;  --->  LOAD R0, x | LOAD R1, y | ADD R0, R1 | STR z

            Terminal Command to stop after Compiling:
````
```bash
                gcc -S file1.c -o out.asm
```
<br>

&emsp;&emsp; ${\color{blue}\text{(1.3)}}$: **Assembler**  
````
            The Assembler translates Assembly instructions into raw binary Machine Code (0s and 1s) 
            based on the Instruction Format Set of the specific CPU.
            It packages this into an Object File (.obj or .o).

            For example, it converts a mnemonic like ADD into an Opcode + Operand (e.g., 10101111).

            Terminal Command to stop after Assembling:
````
```bash
                gcc -c file1.c -o out.obj
```
<br>

&emsp;&emsp; ${\color{blue}\text{(1.4)}}$: **Linker & Locator**  
````
            The Linker mixes/combines all scattered Object files together into a single Executable 
            file (.hex or .exe).
            The Locator (using a Linker Script) specifies the exact physical locations (addresses) 
            for each symbol in Flash memory (e.g., global variables, functions, vector table).
````

<br>

${\color{red}\text{VERY IMPORTANT NOTE: (2)}}$
````
    How does the Linker know how to connect multiple files? It uses a "Symbol Table".
    Each object file has its own Symbol Table (generated by the compiler) detailing what it "Provides" 
    and what it "Needs".

    If File1.c calls Add() but doesn't define it, its state is "Needed".
    If File2.c defines Add(), its state is "Provided".
    The Linker connects the Needed request to the Provided logical address.

    This prevents the two most common build errors:
    1. "Undefined Reference": An object is Needed, but no file Provided it.
    2. "Multiple Definition": An object is Provided by more than one file, confusing the Linker.
````
<br>

&emsp; ${\color{red}\text{(2)}}$: **Memory Sections & Hardware Mapping**
<br>

&emsp;&emsp; ${\color{blue}\text{(2.1)}}$: **Object File Sections** <br>
````
            Object and Executable files are structurally divided into specific isolated memory blocks 
            called "Sections". Every section inherently possesses 3 attributes: Address, Size, and Name.
            
            1. .data: Stores global and static variables INITIALIZED to a specific value (e.g., int x = 10;).
            2. .bss: Stores global and static variables that are UNINITIALIZED (e.g., int x;).
            3. .text (Code): Stores the actual executable machine instructions.
            4. .rodata (Read-Only Data): Stores global constants (const) and string literals.
````

````
            Embedded Memory Architecture Map:

               ROM (Flash Memory)                        RAM (SRAM)
            +----------------------+              +----------------------+
            |                      |              |        Stack         |
            |     .text (Code)     |              |    (Local Vars)      |
            |                      |              |          v           |
            +----------------------+              +----------------------+
            |       .rodata        |              |                      |
            |     (Constants)      |              |      Unused Area     |
            +----------------------+              |                      |
            |    .vector table     |              +----------------------+
            +----------------------+              |        Heap          |
            |        .data         | ======>>     +----------------------+
            |  (Initial Values)    |  Startup     |        .bss          |
            +----------------------+   Copy       |   (Cleared to 0)     |
                                                  +----------------------+
                                                  |        .data         |
                                                  |  (Working Variables) |
                                                  +----------------------+

````


&emsp;&emsp; ${\color{blue}\text{(2.2)}}$: **Allocatable vs. Loadable Sections** <br>
````
            Understanding where a section physically resides during runtime dictates RAM usage.

            Loadable Sections (Moved to RAM):
            These sections require read/write access and must physically be copied or created in RAM 
            during the Startup Code phase.
            - Examples: .data, .bss.

            Allocatable Sections (Permanent in ROM): 
            These sections stay permanently in the Flash (ROM) memory. The CPU fetches instructions 
            and constant data directly from Flash.
            - Examples: .text, .rodata.
            - Note: In standard Computer PC architectures, .text is loadable (moved to RAM), 
              but in Embedded Systems, it is strictly allocatable to save precious RAM.
````

<br>

| Section | Content | Section Type | Flash (ROM) Presence | RAM Presence |
| :--- | :--- | :--- | :--- | :--- |
| **`.text`** | Executable Instructions | Allocatable | Yes (Permanent) | No (Executed in place) |
| **`.rodata`**| Constants & String Literals | Allocatable | Yes (Permanent) | No |
| **`.data`** | Initialized Globals/Statics | Loadable | Yes (Stores initial boot values) | Yes (Active working space) |
| **`.bss`**  | Uninitialized Globals/Statics | Loadable | No (Waste of space) | Yes (Reserved & zeroed by Startup) |
